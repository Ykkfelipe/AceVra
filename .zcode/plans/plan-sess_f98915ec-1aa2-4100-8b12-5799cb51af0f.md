## Goal

Codex backend gets a real, working model selector in the composer: **Default (Codex app setting)** plus the six models you named (GPT-6 Astra / GPT-6 Sol / GPT-6 Luna / GPT-5.6 Sol / GPT-5.6 Terra / GPT-5.6 Luna as slugs `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`). Selection applies when the Codex task is created. Claude is explicitly out of scope (no Claude execution backend exists); mid-session Codex model switching is also out of scope (selection is per new task, thread-level — same boundary the Codex integration already uses).

## 1. Shared contract — `packages/shared/src/codex-execution.ts`

This is the only file allowed to cross the codex-execution channel, so the curated list lives here:

- `CODEX_MODEL_OPTIONS`: readonly `{ id, label }[]` for the six slugs above (ids are sent verbatim to Codex; labels are display-only).
- `CODEX_MODEL_DEFAULT` sentinel semantics: `modelId: undefined/null` = use the Codex app's own default.
- Helpers: `isCodexModelOptionId()`, `codexModelOptionLabel(id)`.
- Extend `CodexExecutionCreateTaskParams` with `modelId?: string` (no tokens, no paths — respects the stated security boundary).

## 2. Codex host service

- `codexTaskRuntime.startCodexThread`: accept optional `modelId`; include `model: modelId` in `thread/start` params only when set (thread-level, mirroring the existing `approvalPolicy`/`sandbox` pattern). **Fail loud** if the installed Codex binary rejects it — no silent fallback that would pretend the choice applied.
- `codexExecutionServiceImpl.createTask`: thread `params.modelId` through; store it as new optional `codexModelId` on `ZCodeTaskMeta` and on the runtime; reflect it in the Codex snapshot `config.model` (empty string when Default) so the UI can display what the thread uses.
- `sendTurn` unchanged (turn-level overrides stay out of scope).

## 3. Composer UI

- Draft persistence: add `codexModelId?: string | null` to `V4ComposerDraft` (localStorage, same as `executionBackend`), with a new `onSelectCodexModel` handler in `useDraftConfigControl`.
- Replace the static "Model managed by Codex" indicator with a new `V4ComposerCodexModelSelect` dropdown (same outline/focus toolbar contract as the backend switch): trigger shows the chosen label or "Codex model"; menu has Default + the six models; disabled when Codex backend unavailable.
- Send path: SessionPane's codex `createTask` passes the drafted `modelId`.
- i18n: en-US + zh-CN for the trigger, "Default (Codex app setting)", and keep the managed-by wording as the Default option's description.

## 4. Specs first (repo rule)

- `packages/ui/specs/composer-toolbar-presentation.md`: replace the "model managed by Codex" display-only section with the per-backend selection contract (Codex curated list, thread-level application, Default sentinel, Claude exclusion).
- `packages/desktop/specs/release-0.1.0-alpha.1.md`: one paragraph under the composer section noting Codex model selection is thread-level and Claude remains excluded.

## 5. Tests

- Shared: list integrity (unique ids, label lookup, unknown-id rejection).
- Services: `startCodexThread` sends `model` only when set; `createTask` propagates to meta + snapshot `config.model`; default omits the field.
- UI: draft store roundtrip for `codexModelId`; trigger-label pure helper; existing codex runtime tests updated for the new optional param.

## 6. Gates and delivery

`pnpm typecheck`, `pnpm lint`, `pnpm architecture:check --changed`, focused tests → commit → fresh local-alpha arm64 build → archive validator → exact five-file handoff → close app → tested installer → relaunch → update `build-info.json`, worklog, and status report. Superseded release dirs cleaned after install; no TCC or broader acceptance work.

## Explicit non-goals

No Claude execution backend or Claude model anything; no reading of `~/.codex/config.toml`; no mid-session switching; no changes to the Agent backend's existing plan-model picker.
